<objective>
Fix BL-01 part 1: the Bubble Tea effort modal silently overwrites blank effort fields with 0.

Purpose: `parseFloat("")` returns `0, nil`, `EffortSubmitMsg` carries plain `float64`, and both
call sites take the address of a local copy — so a blank field arrives at `internal/ado` as a
non-nil pointer to 0.0 and is written as a real zero. `ado.UpdateWorkItemStateWithEffort` already
takes `*float64` and already omits the patch operation for a nil pointer (plan 04-02). The entire
bug is the TUI layer failing to produce nils.

Output: nullable effort values end to end through the TUI, plus tests pinning blank-means-absent
and explicit-zero-means-zero.

## Decision reversal

This reverses `04-CONTEXT.md` **D-17** ("preserve TUI behaviour exactly"), explicitly authorized
by the user. Verified during planning: `TestUpdateWorkItemStateWithEffortIssuesExactPatch`
(`internal/ado/workitems_test.go:341-393`) is the D-17 regression guard but it calls
`client.UpdateWorkItemStateWithEffort` **directly** with three non-nil `*float64` locals — it
never touches the TUI. Because `internal/ado` is not modified, that test must remain byte-for-byte
unchanged and must still pass. **If any task in this plan appears to require weakening or editing
that test, stop — the fix has been mis-scoped. Report it rather than editing the test.**

## Out of scope

- Routing TUI writes through `cmd/adoBizInt`'s `runWrite` for dry-run / `--confirm` / audit
  records. That is BL-01 part 2 and stays in `.planning/BACKLOG.md`.
- Any change to `internal/ado/` — the nullable signature there is already correct.
- The `completed <= 0` validation at `effort.go:144`. Completed remains required and must stay
  required; this plan only changes how a blank Completed is *reported*, not whether it is allowed.
</objective>
