## Mutation targets are NOT uniform

RESEARCH's "All eight follow the identical shape" claim was **corrected in
revision 1**; see the CORRECTION block under §"The Eight Aggregate Reads". Seven
reads swallow by `log.Error(...)` then `continue` in the per-project loop. The
dashboard does not.

| Read | Swallow being pinned | Mutation that must turn the test red |
|------|----------------------|--------------------------------------|
| `GetWorkItems` and the six in 01-05 | `continue` in the per-project loop | Remove that `continue` |
| `GetDashboardCounts` | in-place, one layer down inside `getProjectCounts` | Add `return nil, err` at the `QueryByWiql` error site (`dashboard.go:101-102`) so `getProjectCounts` propagates |

**Removing `dashboard.go`'s `continue` is not a valid mutation.** That branch is
unreachable: `getProjectCounts` returns `nil` error unconditionally at
`dashboard.go:141`. Deleting unreachable code cannot turn a test red, and an
executor attempting it would loop on "if it still passes, fix the test" forever.

The mutation check is not optional. RESEARCH Trap A demonstrates that a
characterization test in this codebase can pass while pinning nothing, and such a
test would survive Phase 2's inversion — hiding exactly the change it exists to
make visible.

## Mutation evidence requirement

A green test plus a clean `git status` looks identical whether the mutation was
performed or skipped, so the automated command cannot enforce this. The SUMMARY
must therefore record, for each mutation:

1. the **mutated diff hunk**, captured with `git diff -- <file>` while the
   mutation is in the working tree, and
2. the **observed `FAIL` output** from the test run under that mutation.

The diff hunk is what makes the evidence checkable — it shows what was actually
changed, not merely that something failed.
