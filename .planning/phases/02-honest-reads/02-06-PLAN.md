<objective>
Close verification gap 1 (BLOCKER) from the 2026-10-12 re-verification. GetPipelineRuns and GetReleases each make a second call per definition (N+1). When that call fails, the error is logged at Debug, the definition is still appended with its default status, and no Failure is recorded. A rejected token or a timeout therefore shows up as "never run" / "no releases" with `complete:true`, and the CLI exits 0. This is the exact empty-versus-failed confusion Phase 2 exists to remove (D-02, TRUST-01, TRUST-03).

Purpose: after this plan, a failed per-definition lookup is reported by name and classified (D-06, D-07). The failed definition is left out of Items, so it can never look like an empty state (decision G1 below, D-13). A fetch deadline that expires partway through the definition loop records a timeout for each definition it did not reach and issues no more calls (D-12).

The plan also closes a fourth swallow of the same class, which the planner found and the coordinator approved on 2026-10-12. In GetPipelineDefinitions, the per-definition detail call (GetDefinition, `internal/ado/pipelines.go:337-350`) drops its error behind `if err == nil && fullDef != nil`. The definition is then returned with an empty `repository_id` and `default_branch` under `complete:true`. The trigger modal uses that repository id to fetch branches (`internal/ui/pipelines/trigger_modal.go:164`), so the failure surfaces later as an unrelated error. Task 3 applies the same treatment as Tasks 1 and 2.

Output: three edited per-definition loops, three new operation-label constants, and six new tests.
</objective>

<decision_in_this_plan>
**G1: a definition whose per-definition lookup failed is omitted from Items. It does not get an explicit "unknown" status row.** This was delegated to the planner by the orchestrator.

Why omit:
- It is the pattern every other read in this phase already uses. Items holds what was fetched and Failures names what was not (result.go's Result doc comment). GetBranches drops a failed repository's branches and records `get branch stats for <repo>`. This plan mirrors that exactly.
- It keeps the 02-04 JSON contract intact. No field is added and no value joins the `status` vocabulary. A consumer switching on `status` meets no unfamiliar value, and a consumer reading `failures` meets the same four-key record it already parses (D-04, T-02-01).
- It needs no change to any view. The pipelines and releases views already render `"could not read: " + styles.SummarizeFailures(...)`, which prints the project, kind and operation (`internal/ui/pipelines/pipelines.go:199`, `internal/ui/releases/releases.go:200`). Because the operation names the definition, the warning line reads, for example, `could not read: P (timeout: get latest build for Deploy-API)`.
- An explicit "unknown" row would add a value to a frozen enum-like field. It would also need a new render branch in two views, which means more code and a contract change.

Known consequence, consistent with D-14 and not a new decision: a per-definition 401/403 is classified `auth`, so `styles.FirstAuthFailure` makes the view show its blocking auth banner. The per-repository branch failure already behaves the same way.

Reversibility: reversible. Rationale is on Task 1.

**G1 applied to GetPipelineDefinitions (Task 3): a definition whose detail lookup failed is omitted, not kept with blank repository fields.** Reasons, in addition to the ones above:
- A kept row would carry an empty repository_id, and the trigger modal would use it to fetch branches (`trigger_modal.go:164`). The failure would resurface later, mislabelled as a branch-fetch problem.
- The view already treats definitions as a secondary fetch. Any Failure sets the status-line warning "Could not load pipeline definitions - trigger may not work" (`internal/ui/pipelines/pipelines.go:291-293`), and the remaining definitions stay usable. No view change is needed.
- Only the err != nil path changes. A detail call that answers with no error but a nil body keeps today's behavior and still yields the row. The existing happy-path fixtures depend on that.

Known edge case, recorded and not changed: the loop guards only d.Name. A matching definition with a nil Id would make the SDK return ArgumentNilError on the client side (build/client.go:1882-1884) before any request is sent. With this change, that is recorded as an other-kind Failure for the definition, where before it produced an ID-0 row with blank repository fields. This errs in the safe direction (noise, never a lost failure), and ADO does not return such definitions in practice. Adding a nil-Id guard here is Phase 5's D-14 scope, and this plan prohibits it.

**Structural test note:** TestCollectedDefinitionsGuardNameAndID counts a range loop only if its body appends the bare range value. The GetPipelineDefinitions loop appends the constructed `def`, not its range value `d`, so it is not counted today and Task 3 does not change that. The exact count stays 2, and nilguard_test.go is not edited.
</decision_in_this_plan>
