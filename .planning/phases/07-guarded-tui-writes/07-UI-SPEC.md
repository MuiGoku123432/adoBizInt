# Phase 7 — UI Design Contract

> Visual and interaction contract for the TUI surfaces of Guarded TUI Writes. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Medium:** this is a Go terminal UI (Bubbletea v1.3.10 + lipgloss v1.1.0 + bubble-table v0.19.2), not a web frontend. There are no px, no CSS and no font sizes. Spacing is in terminal cells (columns x rows), "typography" is weight and colour on a fixed cell grid, and colour is the existing lipgloss palette in `internal/ui/styles` plus the ANSI 256 colours already used by the modal family. Every value below is either taken from existing code or from the approved plans 07-04..07-08; the three places this contract differs from a plan are listed in **Plan Conflicts** at the end and must be applied as plan amendments, not silently.

## Spacing Scale

Unit: one terminal cell (1 column horizontally, 1 row vertically). The template's 4-multiple px scale does not apply to a cell grid; these are the only spacing values this phase uses, all taken from the existing modal family or derived from the 60-rune line cap.

| Token | Value | Usage |
|-------|-------|-------|
| gap-0 | 0 rows | Sticky unknown line sits directly above the status line, no blank row between |
| pad-y | 1 row | Modal vertical padding (`Padding(1, …)`); blank row between title and first diff line; blank row above the key hint (from `HelpStyle.MarginTop(1)`) |
| pad-x | 2 cols | Modal horizontal padding (`Padding(…, 2)`) |
| sep | 2 spaces | Separator between field name and value in a diff line: `<Field>  <From> → <To>` (fixed, not column-aligned; 07-04 `Lines()`, asserted by 07-06/07-07 tests) |
| content | 60 cols | Modal content width = modal line truncation cap (60 runes, 07-04 `New`) |
| modal-w | 64 cols | lipgloss `Width(64)` on the modal frame (content 60 + pad-x 2 x 2). Rendered footprint 66 cols with the border, fits an 80-col terminal. **Plan conflict C1** (07-04 says 56) |
| actions-col | 18 cols | Work Items `Actions` column width, so `staged → Resolved` (17) renders whole. **Plan conflict C2** (currently 10) |

Exceptions: none beyond the cell-grid translation above. The modal has **no fixed height**: it is content-driven (unlike the effort and trigger modals, which set `Height`), so a 1-line and a 5-line diff both render without blank filler.

## Typography

One cell size (the terminal's). Roles are distinguished by weight and colour only.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body (diff lines, status text) | 1 cell | Regular | 1 row |
| Label (key hints) | 1 cell | Regular, `HelpStyle` muted | 1 row |
| Heading (modal title `Confirm #<id>`) | 1 cell | Bold, colour 12, centred in the 60-col content width | 1 row |

Weights used: exactly two, Regular and Bold. Bold is reserved for the modal title. No italic, underline, reverse or blink is added in this phase.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | terminal default background and foreground (unpainted) | View background, table body, modal body text and diff lines |
| Secondary (30%) | `styles.Muted` `#605E5C` (via `SubtitleStyle` / `HelpStyle`); modal border ANSI 256 `62` | Key hints, non-error status on Work Items / Releases / Pipelines, the modal frame |
| Accent (10%) | `styles.Warning` `#FFB900` (via `WarningStyle`) | Staged-edit marker only (see below) |
| Heading | ANSI 256 `12` (existing modal title colour) | Modal title only |
| Destructive / error | `styles.Error` `#D83B01` (via `ErrorStyle`) | Error status lines and the sticky unknown line only |
| Success | `styles.Success` `#107C10` (via `SuccessStyle`) | PRs view non-error status only (existing convention, not extended to other views) |

Accent reserved for: the Work Items `Actions` cell of a row with a staged edit (`staged → <state>`). It is not used for the modal, key hints, status lines or any other element.

Colour is never the only signal: the staged marker carries the word `staged`, every error line carries `FAILED`, `blocked`, `unknown` or `could not read`, and the modal is identified by its title and key hints. The diff lines inside the modal are uncoloured; `From` and `To` are distinguished by position and `→`, never by colour.

## Surfaces and Interaction Contract

### S1. Confirm modal (`internal/ui/confirm/modal.go`, all four write-capable views)

Illustrative render (Work Item Task resolve, 07-07):

```
╭──────────────────────────────────────────────────────────────╮
│                                                              │
│                          Confirm #5                          │
│                                                              │
│  System.State  Active → Closed                               │
│  Microsoft.VSTS.Scheduling.RemainingWork  3 → 0              │
│  Microsoft.VSTS.Scheduling.CompletedWork  (none) → 2         │
│                                                              │
│  [y] write  [n] discard  [esc] stay                          │
│                                                              │
╰──────────────────────────────────────────────────────────────╯
```

| Property | Contract |
|----------|----------|
| Position | Centred over the current view with `modal.Center` (via `Flow.View`) |
| Frame | `lipgloss.RoundedBorder()`, `BorderForeground(lipgloss.Color("62"))`, `Padding(1, 2)`, `Width(64)`, no `Height` |
| Title | `Confirm #<id>` (locked, D-01). Bold, colour 12, `Width(60)`, `Align(lipgloss.Center)`. `<id>` is the batch ID: work item ID, PR ID, release approval ID, or pipeline definition ID |
| Body | One line per field change, in op order, de-duplicated (07-04 `Lines()`): `<Field>  <From> → <To>`. Empty From renders `(none)`. A change on a target other than the title ID is prefixed `#<targetID> ` (User Story dev-task lines, 07-07). Field names are the guard's exact ADO strings (`System.State`, `Microsoft.VSTS.Scheduling.RemainingWork`, `reviewer.vote`, `status`, `approval.status`, `queued_build`); they are not prettified, because they are what the audit record stores |
| Line hygiene | Control runes dropped, then truncated to 60 runes (`utils.Truncate`). At `Width(64)` no line wraps |
| Key hint | `[y] write  [n] discard  [esc] stay` (locked, D-01), rendered once with `HelpStyle` (its `MarginTop(1)` is the blank row) |
| Keys | `y` write; `n` discard; `esc` stay. Every other key, including `enter`, space and `Y`, does nothing (07-04 T-07-14). `q` / `ctrl+c` are held by `app.go` while the flow is busy (07-08); tab keys `1`-`6` are held because `IsTextInputFocused()` is true |
| Not shown | No "loading" frame: the modal opens only after the pre-read returns. No default-highlighted button. No destructive colouring of particular verbs — PR complete, release reject and pipeline queue use the identical modal (D-05) |

### S2. Status line outcomes (every write-capable view)

The status line keeps its existing position and per-view non-error style. `IsErr` maps to `ErrorStyle`; otherwise the view's existing non-error style. Exact copy is in the Copywriting Contract.

| State | Style | Behaviour |
|-------|-------|-----------|
| Pre-read in flight | non-error | All keys swallowed by the flow; auto-refresh skipped (tick only re-armed) |
| No-op (D-07) | non-error | No modal; nothing sent; navigation proceeds (Work Items) |
| Write in flight | non-error | Keys swallowed; quit held (07-08); auto-refresh skipped |
| Executed | non-error | View re-fetches |
| Discarded (`n`) / Not written (`esc`) | non-error | Nothing sent, no audit record (D-04) |
| Failed, changed since preview, preview read failed | `ErrorStyle` | Not sticky; replaced by the next status |
| Audit sink unwritable (D-10) | `ErrorStyle` | Nothing sent; the next write attempt is allowed (writes are not disabled for the session) |
| Unknown outcome (D-08) | `ErrorStyle`, **sticky** | Rendered on its own line directly above the status line; survives refreshes; cleared by the next keypress, which is then also processed normally (07-04). The view re-fetches |

### S3. Staged-edit marker (Work Items only, 07-06 / 07-07)

| Property | Contract |
|----------|----------|
| Where | The `Actions` cell of the staged row, replacing `[n] Next` |
| Text | `staged → <state>` with `<state>` the staged target state as ADO spells it (e.g. `staged → Resolved`) |
| Style | `WarningStyle` (amber). Rows with nothing staged are byte-identical to today |
| Width | Actions column 18 cols (C2). A state name longer than 9 runes is truncated by bubble-table with `…` (e.g. `staged → In Progr…`); the full name is in the status hint and the modal |
| Other columns | The `Status` column keeps showing the current ADO state. It never shows the staged state, because nothing has been written |
| Triggers that open the confirm (D-02) | Row move that changes the highlighted ID; `enter` or `n` on a different row; tab switch `1`-`6`; `q` / `ctrl+c`. The highlight does not move and the tab does not switch until the modal is answered |
| Answers (D-03) | `y` writes then completes the navigation (on executed or all no-op); `n` drops the staged edit then completes the navigation; `esc` cancels the navigation and keeps the edit staged |
| Failure paths | Failed or unknown write: stay on the item, edit dropped, navigation cancelled so the error stays visible (07-06, 07-08). Failed preview (sink or pre-read): edit dropped, stay; the next move is free (T-07-26) |

### S4. Leave and quit prompt (app level, 07-08)

There is no separate app-level prompt. Tab switch and quit with a staged edit open **the same confirm modal (S1)** for the staged item, then replay the tab key or quit only when the view emits `ProceedMsg`. While any view's flow is busy, `q` and `ctrl+c` do nothing; the visible feedback is the existing in-flight status text (`Checking …` / `Writing …`) or the open modal's key hints. No additional "quit held" copy is shown.

### S5. Input-then-confirm (Releases, Pipelines, D-06)

The existing approval-comment modal and trigger modal are unchanged. Submitting them closes the input modal, shows the pre-read status, then opens S1. The two modals are never on screen together.

## Copywriting Contract

Locked literals from 07-CONTEXT.md are marked **(L)**. All other strings are the approved plan strings, kept verbatim, except the first-part rule (C3).

| Element | Copy |
|---------|------|
| Primary CTA | `[y] write` inside `[y] write  [n] discard  [esc] stay` **(L)** |
| Modal title | `Confirm #<id>` **(L)** |
| Diff line | `<Field>  <From> → <To>`; empty From is `(none)`; other-target prefix `#<targetID> ` |
| Empty state heading | Not applicable: the modal never opens with zero changes. A zero-change pre-read is the no-op status below |
| Empty state body | `No change: #<id> already <label>` **(L, D-07)**, e.g. `No change: #7 already approved`, `No change: #1 already resolved`. An abandoned PR on complete reads `No change: #<id> already abandoned` (not `already completed`) |
| Pre-read status | PRs `Checking PR #<id>...`; Releases `Checking approval #<id>...`; Pipelines `Checking <PipelineName> on <Branch>...`; Work Items `Checking #<id>...` |
| Write in flight | `Writing #<id>...` |
| Staged hint | `#<id> staged: <state> — move to another row to confirm` |
| Kept after esc (Work Items) | `#<id> still staged — move on to confirm` |
| Not written after esc (single-shot views) | `Not written: #<id>` |
| Discard after n | `Discarded: nothing written for #<id>` |
| Executed | `#<id> <label>[; <label>…]`, e.g. `#7 approved`, `#7 completed`, `#42 rejected`, `#9 queued on main`, `#1 resolved`, `#5 closed; effort update` |
| Error state: audit sink | `write blocked: audit log not writable: <path>` **(L, D-10)**. Problem + path; the user fixes the file or directory permissions and retries |
| Error state: pre-read failed | `#<id>: could not read before writing: <error, control runes dropped, ≤120 runes>` |
| Error state: unknown (single op, or first op) | `#<id>: outcome unknown — verify in ADO` **(L, D-08)**, sticky. Suffix ` (not recorded in audit log)` when the audit append also failed |
| Error state: compound partial (D-09) | `#<id> closed; effort update FAILED: <error>` **(L prefix)**; unknown second write: `#<id> closed; effort update: outcome unknown — verify in ADO` (sticky) |
| Error state: write failed (single op, or first op) | `#<id>: write FAILED: <error>` |
| Error state: changed since preview (single op, or first op) | `#<id>: not written — changed since preview; press the action key again to re-check` |
| Later op not run | `<label> not attempted` as a later part, e.g. `#5: write FAILED: <error>; effort update not attempted` |
| Destructive confirmation | PR complete (merge), PR approve, release approve, release reject, pipeline queue, work-item state change, effort update: all use S1 with `y` as the only write key. No typed confirmation, no second prompt |

**First-part rule (C3).** Labels are past-tense success words (`approved`, `closed`, `queued on main`). A part that did not execute must not open with a success word. So when the first op of a batch is `unknown`, `failed` or refused as changed-since-preview, its part attaches to the ID with a colon and carries no label (rows above marked "single op, or first op"). Parts after the first keep `<label> …` exactly as 07-04 specifies, which is what produces the D-09 literal. Executed and no-op parts are unchanged (`<label>`, `<label> (no change)`).
