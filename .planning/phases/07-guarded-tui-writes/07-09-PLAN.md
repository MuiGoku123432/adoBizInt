## Design decisions (made while planning; each is rated)

| ID | Decision | Why | Reversibility |
|----|----------|-----|---------------|
| G-01 | The WaitGroup `Add(1)`/deferred `Done()` lives inside `confirm.Execute`, never in `Flow.Update` | The eventLoop's `select` can drop a cmd once `p.ctx` is done. An `Add` in Flow with no matching `Execute` would make `Wait` hang forever. Inside `Execute`, every `Add` has a deferred `Done`, including when a `Plan` panic unwinds through it | reversible: one function |
| G-02 | The parent is a package-level `writeParent` set through exported `confirm.SetParent`, not threaded through `ui.NewModel`, the four views and `Flow.Start` | Threading means changing the NewModel signature, four view constructors, every `Flow.Start` call site and their tests. That is a large blast radius for one process-level value. The WaitGroup is already process-level state in `confirm` | reversible: two exported funcs in one package; threading later touches only confirm and main |
| G-03 | The signal context is NOT handed to the bubbletea program as its program context | Checked in tea.go: the program's signal goroutine sends `QuitMsg` with a bare blocking send. When the signal also cancels the program context, the event loop can exit on `ctx.Done()` first, leaving that send blocked forever. `shutdown` then waits on the handler channel forever, before `restoreTerminalState`, so the TUI hangs with a raw terminal. It would also turn a SIGTERM exit from 0 into an `ErrProgramKilled` exit 1 | reversible: one line in main |
| G-04 | `confirm.Wait()` sits immediately after `p.Run()` and before its error branch | `Run` returns an error after a panic it recovered (Update or a cmd goroutine). That is the case where another goroutine may be mid-write, so the wait must cover the error path too | reversible |
| G-05 | `NotifyContext` is registered just before `p.Run()`, and its stop is deferred until `run` returns | A late registration keeps the window before bubbletea installs its own handler short (residual R2). The deferred stop keeps SIGINT/SIGTERM captured through `Wait`, so a second SIGTERM is absorbed and cannot kill the process mid-append. The CLI works the same way. The deferred stop also cancels the write parent as run returns (NotifyContext's stop func calls cancel), which is what bounds the late-start window in T-07-38 and R1 | reversible |
| G-06 | `Preview` uses `writeParent` but is not counted in `inflight` | With no Confirm, a preview is a dry run: it sends no mutation and writes no audit record, so exiting during it loses nothing. Using the parent lets a signal abort a slow pre-read | reversible |

No decision here is `costly` or `one-way`. The audit record format and the outcome vocabulary are unchanged (`unknown` already exists), and no published contract moves. So there is no `checkpoint:decision` and the plan stays `autonomous: true`.

## Known residuals (recorded explicitly, not dropped)

- **R1. Late start after Wait.** Two cases reach it. Bubbletea recovers a panic after Update returned the Execute cmd, or a signal's QuitMsg ends `p.Run` before NotifyContext's goroutine has cancelled the parent. If the cmd's goroutine then reaches `inflight.Add(1)` only after `Wait` returned, `Wait` returns with nothing counted and the late goroutine starts with a parent that is still live. It cannot send a mutation until it has opened the sink and completed a full pre-read HTTP round trip. Meanwhile main runs only the few statements between `Wait` and `return`. Then the deferred `stopTUISignals()` cancels the parent (NotifyContext's stop func calls cancel), and `os.Exit` follows. The pre-read is therefore cut short by the cancel or still in flight at exit, and either way nothing is sent. What is left is a timing argument, not a structural guarantee: a pre-read round trip that completes inside that window. Accepted, low (T-07-38).
- **R2. Startup window.** A signal that arrives after `NotifyContext` registers but before bubbletea's handler is installed inside `p.Run` is absorbed. The TUI starts with a cancelled write parent, so every write in that session is refused at its pre-read: nothing is sent and there is nothing to audit. Accepted, low (T-07-40).
- **R3. Uncatchable or unhandled ends:** SIGKILL, SIGHUP and power loss. Parity with the CLI. Accepted (T-07-41).
- **R4. Silent wait after a recovered panic.** With a write in flight, the process can wait up to that write's budget after the terminal is restored, and it prints nothing. Adding copy for this is out of scope. Accepted (T-07-39).
